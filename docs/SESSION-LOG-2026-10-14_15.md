## Part 1 — Start pacing (2026-10-14)

The complaint: on a phone the fish swam through empty water for **3.4 s (16:9) / 4.1 s (19.5:9)**
before the first rocks arrived. Dead time.

Three levers, all serialized fields that already existed. No new code.

| Field | Was | Now |
|---|---|---|
| `GameManager.startFractionFromLeft` | 0.3333 | **0.3** |
| `TrashSpawner.startSpeedMultiplier` | 0.7 | **0.9** |
| `TrashSpawner.maxSpeedMultiplier` | 1.6 → 1.9 → | **1.6** |
| `TrashSpawner.rampSeconds` | 90 | **150** |
| `CoinSpawner.rampSeconds` | 90 | **150** |

### The maths that drove it

Dead distance `D = HalfWidth × (2 − 2f) − 0.05`, wait `= D ÷ (5 × startSpeedMultiplier)`.
Camera is orthographic size 5, rocks move at 5 u/s, rows start at `CameraEdges.Right + 0.5`.

Reaction window at full difficulty is the same distance divided by `5 × maxSpeedMultiplier`, and
it is the number that pays for a shorter opening. Every change to the fish's position was weighed
against it:

| `startFractionFromLeft` | First rock (16:9) | Reaction at full difficulty |
|---|---|---|
| 0.6 | 1.41 s | **0.89 s** — frantic, rejected |
| 0.5 | 1.77 s | 1.11 s |
| 0.45 | 1.95 s | 1.22 s |
| **0.3** | **2.48 s** | **1.56 s** |

0.3 is roughly where Flappy Bird puts the bird. The screenshot annotation "1 2 3 — cave shows up"
matched 2.48 s, which is why `startSpeedMultiplier` was left at 1.0 at that point.

### The ramp was the real problem

Distance is scored at `unitsPerSecond × SpeedMultiplier`, so a 90-second ramp **finished at 585 m**.
At 200 m the game was already **40 % of the way to maximum difficulty**. The instinct that 200 m is
where it should *start* biting was right; 200 m was where it was already biting.

`rampSeconds` 90 → 150 stretches the whole curve:

| Distance | Speed before | Speed after |
|---|---|---|
| 0 m | 1.00× | 0.90× |
| 200 m | 1.24× | **1.09×** |
| 400 m | 1.45× | 1.25× |
| Full difficulty at | **585 m** | **937 m** |

**`CoinSpawner` has its own `rampSeconds`** driving coin rate only. Left at 90 it would reach full
coin density while the cave was still half speed. Both were moved together.

`maxSpeedMultiplier` was briefly 1.9 and briefly **1.19** (a typo caught by reading the scene back,
which had flattened the ramp to 0.7 → 1.19). Settled at 1.6, which also re-validates the code's own
warning: *"at full difficulty the cave is already at 8 units/sec"* — true at 1.6, false at 1.9.

## Part 2 — Three lessons about Unity, paid for the hard way

### 1. Inspector edits during Play mode are discarded

Typed values appeared to do nothing, twice, because Play was running. **Edit mode only, then Ctrl+S.**
Now the first thing checked whenever a value "did not apply".

### 2. A new `[SerializeField]` on a component already in the scene comes back EMPTY

The `skins` array was written straight into the YAML and Unity re-saved it as `skins: []` — it had
loaded the scene *before* compiling the new field, ignored the key, then written the field back as
empty. Re-running after the assembly was compiled made it stick.

The same trap is why `PlayerController`'s idle-bob values are **consts, not serialized fields**: a
zero there is exactly the frozen fish the feature exists to fix.

### 3. Unity only recompiles when the Editor regains focus

A stale `Assembly-CSharp.dll` (built 78 seconds before the source was saved) reported an error from
code that no longer existed. Compare the DLL's timestamp against the `.cs` before believing a stack
trace.

## Part 3 — In-game fish skins

Picking a fish in the shop wrote `PlayerPrefs["FishEquipped"]`, and **nothing read it**.

### The wiring

- `PlayerController.ApplySkin()` reads the pref and sets the child `Animator`'s SpriteRenderer.
- Called from `ResetPlayer()` — which both `StartGame()` and `BackToMenu()` route through, so one
  place covers the run fish and the menu fish.
- Also called from `GameManager.ShowCharacters()`. Closing the shop goes through neither of those,
  so without it the menu fish kept the old skin until the next run.
- Read from PlayerPrefs, **not** `FishInventory.EquippedIndex`: the shop panel is inactive at scene
  load, so its `Awake` has not run and the property reads 0 whatever the save says.
- `FishInventory.EQUIPPED_KEY` was made `public` so the key lives in one place.

### The ordering bug, and why filenames caused it

`FISH1–4.png` are **not** numbered to match `PEIXE1–5.png`. Every card was opened and matched
against every skin by artwork:

| Block | Card | Fish | Skin |
|---|---|---|---|
| 0 | PEIXE1 | Abyssal Chomper — dark purple | `Frame 1 (1)` |
| 1 | PEIXE2 | Corsair Chomper — eyepatch, gold hoops | `FISH1` |
| 2 | PEIXE3 | Crimson Hunter — skeletal fins | `FISH4` |
| 3 | PEIXE4 | Mossy Scavenger — rust and sea moss | `FISH2` |
| 4 | PEIXE5 | Metal Chomper — pale silver | `FISH3` |

Ruled out first, so the fix landed in the right place: `Content`'s children are in order
(sibling 0–5 = Block 1–6), `fishArt` is wired PEIXE1→PEIXE5 in order, and `OnBlockClicked(index)`
writes the block's own child index.

`FISH4` was originally the **blue** fish, which no card describes. It was held as a `null` slot —
**never dropped**, because removing the entry would shift every later fish onto the wrong card, the
exact bug being fixed. The red Crimson Hunter later replaced it and the blue one became `FISH5`,
still unused.

Each line of `SKIN_PNGS` now names the card it belongs to. Matching on filenames alone is what put
the wrong fish in the cave.

## Part 4 — The shop, rebuilt for a phone

Scaled ×1.15 and re-laid out. `Content` has a HorizontalLayoutGroup and a ContentSizeFitter, so
resizing the blocks re-spaces the shelf on its own.

| Object | Was | Now |
|---|---|---|
| Block 1–6 | 540×628 | **620×722** |
| ActionButton ×6 | 288×76 | **330×87** |
| PriceText ×6 | 345×92, font 68 | **397×106, font 78** |
| Scroll View | 1820×700 at y 0 | **1820×810 at y −30** |
| Shelf spacing / padding | 60 / 40 | **69 / 46** |
| CloseButton | 280×76 | **deleted** |
| WalletText | 397×92 top-left | **300×92 top-right** |
| BackButton | — | **197×146 top-left** |

### The top row

`CloseButton` was built from `Select Button.png`, so it rendered the word **SELECT** in the
top-right and read like a card action rather than the way out. Deleted outright — nothing
referenced it but `CharactersMenu`'s child list.

`BackButton` was **cloned from it** rather than built from parts, because its Button already carried
the persistent call `ShowCharacters(false)`. The clone inherits the wiring with nothing to rewire
and no chance of pointing at the wrong method or the wrong bool.

`verify_scene.py`'s assertion was moved from `CloseButton` to `BackButton` — the check has to follow
the button that actually closes the shop, or the real exit goes unguarded.

### Two coin-wallet bugs, both self-inflicted

1. **Right-aligning the label split it from its icon.** `BuildCoinIcon` pins the coin to the box's
   **left** edge and reserves a left margin for the digits — correct only while the text is
   left-aligned. Right-aligning pushed the digits to the far edge, 397 units from the coin. Fixed by
   narrowing the box to 300 and putting the alignment back to Left.
2. **The wallet sat 22.5 units below the arrow.** `BackButton` had been nudged in the Editor to
   y −37.5 from the −60 the script wrote. The script now **derives** the wallet's y from the
   button's real y, height and pivot, so nudging the button and re-running realigns them.

## Part 5 — The background seam, again

A thin bright line swept across the background and blinked in and out.

The earlier fix — deriving X from a shared clock instead of accumulating — held; the maths was not
the problem this time. The residual is a **sub-pixel seam**: adjacent copies abut *exactly*, so
wherever the join lands between pixels neither quad covers that column fully. The camera clears to
a **blue-grey** `(0.19, 0.30, 0.47)`, far lighter than the cave, so the hairline reads as a flash.

`ScrollObject` now lays copies `SEAM_OVERLAP = 0.02` units closer than their own width. The same
trick `ObstacleSpawner` already uses on rocks (`overlap: 0.2`), for the same reason.

## Part 6 — Touch, audio and the menu fish

### Buttons were dead at random on the phone

`EventSystem.m_DragThreshold` was **10** — Unity's mouse-era default. On a touchscreen a finger
drifts further than that during an ordinary tap, Unity reclassifies the tap as a drag, and the
click never fires. Set to **30**. Fixed every button at once, not just the sound one.

Checked and ruled out first: the input module is `InputSystemUIInputModule` (correct for the new
Input System), and both sound buttons resolve to ~351×146 through their AspectRatioFitter, so the
serialized `width: 0` is normal and the tap targets were never too small.

### Sound effects

Two clips in `Assets/Music/`, wired to `GameManager` in the Inspector:

- **Button Click** — `BuildSound()` subscribes **all 17 buttons** under the Canvas to `PlayClick`
  at `Awake`, inactive ones included (the shop's six badges are switched off at load). Done in code
  rather than per button in the Inspector, so a button added later is covered.
- **Coin Clip** — played inside `AddCoin()`, not `CoinPickup`. Every collected coin routes through
  it, behind its existing `isGameOver` guard, so a coin touched on the fatal frame stays silent.

The `AudioSource` is added at **runtime** (`gameObject.AddComponent`), so no component had to be
added to the scene. Muting needed no work at all: `ApplySound()` already drops
`AudioListener.volume`, exactly as its old comment predicted. `PlayOneShot` ignores `Time.timeScale`,
so the menu and the pause screen still click at timeScale 0.

`clickClip` was later renamed to `buttonClick` to match the file, with
`[FormerlySerializedAs("clickClip")]` — without it the rename reads as a new field and the
already-dragged clip comes back empty.

### The sound button, moved twice

First made to stay up through the whole run, then **reverted**: it belongs to the start menu and the
pause screen only. `ShowRunButtons` owns the toggle again. The extra `ShowPauseDim` raise argument
was dropped as redundant — `Raise()` lifts the whole canvas-level ancestor, and Restart/Home/Resume
are siblings in the same `Pause Buttons` group, so the sound button already comes up with them.

### The menu fish now floats

It hung dead still because `BackToMenu()` sets `Time.timeScale = 0f`, which stops `FixedUpdate` and
the Rigidbody2D with it. **`Update` still runs at timeScale 0** — only `FixedUpdate` is gated — so
`MenuIdle()` moves the transform directly off `Time.unscaledTime`.

- Rebuilt from `homeY` every frame, never accumulated. A menu can sit for minutes, and accumulation
  is what walked the background out of step in Part 5.
- Scoped to the menu through a new `GameManager.OnMenu` property, **not** to "frozen": pause and
  game over are frozen too, and a fish still drifting there reads as the pause not having taken.
- Y and tilt only. X belongs to `homeX` and the surge system.
